# SWAFTO — Retail Desk V1

An offline-first day-close app for small Indian retail shops. A shopkeeper who closes
the day on paper enters the same nine sections here — opening cash, sales, udhar
collected, purchases, expenses, withdrawals — and the app says whether the cash drawer
agrees with the ledger. It is built for a ₹7,000 Android phone with no signal, in
Odia, Hindi and English, for someone between 35 and 70 who has never used an
accounting app and does not want one.

**It is not a bookkeeping product.** It answers one question at the end of one day:
*does the cash add up, and if not, by how much.*

## The walkable path

```bash
npm install

npm run check:all            # 15 governance and correctness checks
npx vitest run               # the test suite
npm run coverage             # branch coverage for the engine and the backend
npm run test:vectors:node    # the golden vectors under Node
npm run test:vectors:hermes  # the same vectors under real Hermes
npm run test:vectors:diff    # the divergence between them, which must be zero
```

**There is no app to run yet.** No React Native project exists; the engine, the
schema, the SMS layer and the whole verification harness do. That ordering is
deliberate, and what was deferred to get here is in

## Five rules a new contributor would otherwise break

**1 · No AI, inference, prediction, autocomplete, voice or camera in data entry.**
Not a performance decision and not subject to the usual trade-offs. A shopkeeper must
be able to point at a number and say where it came from. A guessed figure in a cash
ledger is worse than no figure.

**2 · Money is integer paise. Always.**
No floats, no decimal literals, no `parseFloat`. `npm run check:money` is a real
ESLint rule over the whole engine and it fails the build. Division and averaging go
through the audited helpers in `packages/formula-engine/src/money.ts`, the only place
rounding happens.

**3 · Entries are append-only.**
A mistake is corrected by a new row referencing the old one, never by an update or a
delete. Enforced by database triggers on both SQLite and Postgres, and tested by
planting a defect on four different columns — because a trigger narrowed to one
column looked fine for two iterations.

**4 · Totals are derived, never stored.**
There is no `total` column anywhere and there must not be. A stored total is a second
source of truth that drifts silently.

**5 · Every shared value has one home, in `@swafto/values`.**
If a number appears in two documents, or in a document and in code, it belongs in the
registry. `npm run check:registry` fails when a document disagrees with it. This rule
exists because an OTP lifetime was 5 minutes in one audit, 10 in another, and 10 in
the message the user actually received.

## How this repository thinks about evidence

The short version, because it explains a lot of what otherwise looks like
over-engineering:

- **A check that has never failed has never been tested.** Every verifier carries a
  plantable defect, and `npm run prove:verifiers` plants each one and requires a
  failure.
- **An instrument must also respond.** `npm run responds:verifiers` changes the world
  in a known direction and requires the number to move. A mutation harness that
  reported an unchanged score after four tests were added that provably kill one of
  its own reported survivors is not measuring anything — that is a real finding here,
  not a hypothetical.
- **Status is derived, never asserted.** Nothing is true because a file says so.
- **A benchmark with no instrument cannot be claimed met**, and the build fails if one
  is.
