02 -- THE CENTRAL DECISION

The engine is specified once and implemented twice

This is the architectural consequence of being offline-first and correctness-first at the
same time, and it is the part most likely to be got wrong by a team in a hurry.

Offline-first means the phone must compute every figure without asking anyone --
otherwise the app is useless in bad signal, which is most of the time. Correctness-
first means something independent has to be able to say the phone got it right.
Those two requirements force the same arithmetic to exist in two runtimes, and the
naive resolutions are both wrong: sharing code across Dart and the server language
creates a build coupling you will regret, and letting them drift creates two truths
about a shopkeeper's money.

SWAFTO · System Architecture & DFD · V1                                                                                     3
The resolution: one specification, one test-vector file, two implementations

Write the rules once as a plain-text specification with a companion
 vectors.json -- a few hundred worked examples, each a set of entries and
every figure they should produce. Both implementations import that same
file as their test fixture. CI fails if either one disagrees with a vector. You get
independent implementations that cannot silently diverge, without coupling
two codebases, and the vectors become the artefact a new developer reads
to understand the product's actual rules.

RULE UNDER TEST  VECTOR MUST PROVE

Cash equation    Only Cash -mode expenses and purchases reduce the cash balance; UPI, Other,
                 Udhar and Shop stock do not -- while all five still count toward total expenses.
Withdrawal       Reduces cash, never appears in expenses, never touches profit.
Carry-forward
Missed day       Day N opening equals day N-1 counted closing, never the expected figure.
Correction
                 A gap produces a not_closed day and never an interpolated balance.
Skip vs empty
                 An adjustment posted on day N referencing closed day N-3 changes day N's
                 figures and leaves N-3 byte-identical.
                 A skipped section and an untouched section produce the same total and different
                 day states.

      There is no totals table, and there never will be

     Every figure in this document -- cash received, expected balance, net sales,
     a customer's outstanding, a month's profit trend -- is computed from D1 and
     D2 at read time. Caching them is the standard optimisation and the standard
     way a ledger ends up displaying a number that no longer matches its own
     entries. At 25 entries a day the computation is free; the staleness would not
     be.

07 -- CROSS-CUTTING RULES

Six invariants that hold at every layer

If a change would break one of these, it is not a change -- it is a different product.

01 The local write is the write

          A save commits to SQLite and the UI proceeds. No spinner, no optimistic-then-rollback,
          no network in the critical path. Sync is a background consequence, never a
          precondition.

02 Every write is idempotent

          Client-generated UUIDs mean the outbox can retry forever without creating a duplicate
          entry. This is what makes rule 1 safe, and it is the single most commonly skipped piece
          of offline-first plumbing.

03 Nothing derived crosses the wire

          The API exchanges entries, day records and parties. It never returns a computed total
          for display. One engine on the phone produces every number the shopkeeper reads,
          which is why the app is complete offline including its reports.

04 Append-only, forever

          No UPDATE and no DELETE on D1. Corrections are new rows that reference old days.
          The entry log is the source of truth and every screen is a projection of it.

05 One shop, one phone

          An explicit non-goal for V1, stated so nobody builds conflict resolution for a case that
          does not occur. Revisit only when a real shop asks for a second device, and treat it as a
          genuine architectural change rather than a setting.

SWAFTO · System Architecture & DFD · V1                                                              8
06 Divergence is an alarm, not a repair

          When the server's recomputation disagrees with the client's, the server does not
          overwrite. It records both and raises. A money app that silently corrects itself is a
          money app whose bugs you never find.

09 -- DELIBERATE ABSENCES

What this architecture does not have

Listed because every one of them is something a reviewer will ask about, and each
absence is a decision rather than an oversight.

SWAFTO · System Architecture & DFD · V1                                                                 9
NOT PRESENT                              WHY

Any AI or ML in the request path Decision 1. Also the evidence that manual entry builds a stronger habit than
                                                            low-burden capture.

A message queue                          The outbox on the device is the queue. A server-side broker at 600,000
                                         requests a month is infrastructure looking for a problem.

A cache layer                            Nothing is expensive enough to cache, and a cache over derived figures
                                         would reintroduce exactly the staleness section 06 exists to prevent.

Microservices                            One domain, one team of interns, one deployable. Service boundaries cost
                                         more than they save below about ten engineers.

Real-time / websockets                   One shop, one phone. There is no second client to push to.

A payment rail or bank                   V1 records money that has already moved. Nothing in this system can
integration                              move a rupee, which removes an entire class of risk and regulation.

Item or inventory tables                 Decision 5. No input collects them, so no store holds them.
