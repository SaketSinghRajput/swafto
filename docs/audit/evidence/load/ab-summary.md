# A/B load: wave 2 base `85eb766` (before) vs the final wave 3 code (after)

Generated by `tools/load/run.mjs`, six runs interleaved (before, after, before, after, before, after), same seed, same machine, nothing else running. Memory mode: **excludes PostgreSQL.** Mix `planned`, 1 s mean think time per VU, 2000 shops x 60 days, 8 s warm-up then 40 s measured per step.

"before" is `85eb766` checked out in a git worktree, with ONE harness-only change: its in-memory repository got the per-shop index that wave 3 added (`db/memory.ts`), because without it the twin scans every shop's entries per read and would measure the twin, not the API. Everything else in `apps/api/src` is byte-identical to `85eb766` (checked with `diff -r`).

`CPU ms/request` = server CPU (share of one core, from `process.cpuUsage`) divided by throughput: the cost of one request, independent of how loaded the step was. A step is *saturated* when p95 > 100 ms.

After / before, median CPU per request: **-4.2 %** (0.755 vs 0.788 ms). **This is within noise, not a measurable difference**: three runs per build, and their ranges overlap (after ran 0.723 to 1.241, before 0.779 to 0.789).

## Reading it

- **The after-build does not measurably use more CPU per request.** At the 750 step it costs about the same (median above, within noise); both builds spend about 0.75-0.79 ms of server CPU per request on this machine, most of it the HTTP stack (the earlier profile put 31 % of CPU in socket writes on Windows).
- **One after run (rep 3, step 750: 1.24 ms/request, p95 383 ms) is unexplained.** The same build did 0.72-0.76 ms in reps 1 and 2 at that step and 0.90 ms at step 900 rep 2, but nothing was recorded that says why rep 3 was slow, so it is not attributed to the host or to the code. Both builds also show slow episodes at the saturated 900 step (before: reps 1-3 all saturated; after: reps 1 and 3), so the 900 rows say only that one core saturates between roughly 650 and 870 req/s here.
- The p95 < 300 ms target is **not** evidenced by these runs: they exclude PostgreSQL and the network. They show only that the API process is not the limit below about 740 req/s at 1 s think time.
